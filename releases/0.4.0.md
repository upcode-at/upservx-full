## Release v0.4.0 - VM Network Isolation & VLAN Support 🌐

**Release Date:** 2026-04-04

### 🎉 What's New in UpservX v0.4.0

This release extends the virtual machine networking stack with two new capabilities: VLAN tagging for bridge-mode interfaces and full lifecycle management of isolated internal libvirt networks. VMs can now be placed into private L2 segments that are completely invisible to the host network — all IP addressing happens inside the machines themselves.

---

### ✨ New Features

#### 🔖 VLAN Support for Bridge-mode VMs
Virtual machines using bridge mode can now be assigned an 802.1Q VLAN tag. This allows multiple isolated network segments on the same physical interface without separate hardware.

- VLAN ID (1–4094) is configurable in the **Create VM**, **Edit VM** and **Import VM** dialogs
- On first use, the backend automatically creates a tagged sub-interface on the host (e.g. `eth0.100`) via `ip link add ... type vlan id ...` and brings it up
- The sub-interface is attached to a dedicated Linux bridge so libvirt can use it normally
- VLAN ID is stored in the VM registry and correctly pre-populated when editing an existing VM
- If no VLAN ID is set, the interface falls back to untagged bridge mode (existing behaviour)

**Backend implementation:**

- `ensure_vlan_interface(parent, vlan_id)` — idempotent helper; creates the sub-interface only if it does not already exist
- `VirtualMachine`, `VirtualMachineCreate`, `VirtualMachineUpdate` models extended with `vlan_id: int | None`
- `create_vm`, `update_vm` and `import_vm_ova` pass `vlan_id` through to the host-interface setup logic

#### 🔒 Internal VM Networks
A new **Internal Network** mode is available alongside NAT, Bridge and None. Machines attached to the same internal network can communicate on L2, but the host routes no traffic in or out — making it suitable for isolated backend clusters, test environments and inter-VM communication without exposing any port on the host.

**Network management:**
- Networks are pure L2 libvirt networks — no `<ip>` element, no DHCP, no forwarding directive in the XML
- Created with a single name; the bridge interface name (`virbr-<name>`) is assigned automatically
- Networks are started immediately on creation and can be stopped/started independently of any VM
- The built-in `default` network is protected and cannot be deleted

**Manage Networks dialog (VM dashboard):**
- Accessible via the **Networks** button in the VM toolbar
- Table shows all defined libvirt networks: name, subnet (if any), DHCP range, type, active/inactive status badge, and Start / Stop / Delete actions
- Create form accepts only a network name — no subnet or DHCP configuration required
- Start and Stop are idempotent: starting an already-active network or stopping an already-inactive one returns success without error

**VM integration:**
- Select *Internal Network* in the network mode dropdown when creating, editing or importing a VM, then choose the target network from a dropdown populated live from the API
- The **Manage Networks** shortcut is available directly inside the VM dialog for quick access
- The `network_bridge` field in the VM registry stores `network:<name>` for internal-mode VMs; `openEdit` detects this prefix and restores the correct mode on edit

### 🖥️ CLI (`upservx-cli`)

The `upservx` command-line tool ships as a standalone component (Python 3, installed to `/usr/local/bin/upservx`). It communicates with the backend API and is version-bumped to **0.4.0** alongside the rest of the project.

#### Available Commands

| Command | Description |
|---|---|
| `upservx auth login` | Authenticate against the API (prompts for username + password) |
| `upservx auth logout` | Clear stored credentials |
| `upservx auth whoami` | Display the currently authenticated user |
| `upservx service status\|start\|stop\|restart` | Manage the UpservX systemd service |
| `upservx containers list` | List all Docker containers |
| `upservx containers start\|stop\|restart\|remove <name>` | Container lifecycle management |
| `upservx containers logs <name> [--lines N]` | Tail container log output |
| `upservx containers inspect <name>` | Show container details |
| `upservx system info` | Display CPU, memory, storage and kernel information |
| `upservx system stats` | Show live resource utilisation |
| `upservx apps list` | Browse the App Store catalogue |
| `upservx apps info <app>` | Show app details |
| `upservx apps install <app>` | Install an app from the store |
| `upservx backup list` | List all backups |
| `upservx backup create [--target <name>]` | Trigger a new backup |
| `upservx backup status` | Show scheduled backup job status |
| `upservx logs show [-n N]` | Print the last N lines from the activity log |
| `upservx logs follow` | Tail the activity log in real-time |

#### Authentication

The CLI supports two auth methods, resolved in order:

1. **Bearer token** — set via `UPSERVX_TOKEN` env variable or stored in `~/.config/upservx/config.json`
2. **Basic auth (base64)** — stored after `upservx auth login`; credentials are Base64-encoded and sent as `Authorization: Basic ...` on every request

The API URL defaults to `http://localhost:9500` and can be overridden via the config file or `UPSERVX_API_URL` environment variable.

#### Version bump

`VERSION` in `cli/main.py` updated from `0.3.0` → `0.4.0`.

### ⚙️ API Changes

**New endpoints:**

| Method | Path | Description |
|---|---|---|
| `GET` | `/vm-networks` | List all defined libvirt networks (active and inactive) |
| `POST` | `/vm-networks` | Create a new isolated internal network |
| `DELETE` | `/vm-networks/{name}` | Stop (if active) and permanently delete a network |
| `POST` | `/vm-networks/{name}/start` | Activate a defined but inactive network (idempotent) |
| `POST` | `/vm-networks/{name}/stop` | Deactivate an active network (idempotent) |

**`GET /vm-networks` response schema (per network):**
```json
{
  "name": "vmnet1",
  "active": true,
  "autostart": false,
  "details": {
    "forward_mode": "isolated",
    "subnet": "",
    "dhcp_range": "",
    "bridge": "virbr-vmnet1"
  }
}
```

**`POST /vm-networks` request body:**
```json
{ "name": "vmnet1" }
```

**Changed VM endpoints:**

| Endpoint | New fields |
|---|---|
| `POST /vms` | `vlan_id: int \| null`, `network_name: str \| null` |
| `PUT /vms/{name}` | `vlan_id: int \| null`, `network_name: str \| null` |
| `POST /vms/import` | `vlan_id: int` (0 = none), `network_name: str` (empty = none) |

`network_mode` now accepts `"internal"` in addition to `"nat"`, `"bridge"`, `"unconfigured"` and `"none"`.

### 📦 Upgrade Notes

No database migration or manual configuration is required. The new endpoints are registered automatically on backend startup.

**libvirt requirement:** Internal network management relies on `virsh` being available and the backend process having permission to manage libvirt networks (the user running `upservx-service` must be in the `libvirt` group, which is already required for VM management).

**VLAN requirement:** Creating VLAN sub-interfaces requires the backend to have permission to run `ip link` commands. When running under `sudo` this works out of the box; in restricted environments ensure `CAP_NET_ADMIN` is granted to the process.

Existing VMs are unaffected — all new fields default to `null` / `None` and the previous network behaviour is preserved.
