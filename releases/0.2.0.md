## Release v0.2.0 - Notifications, Activity Logging & Cluster Replication 🔔

**Release Date:** 2026-02-26

### 🎉 What's New in Upcode Harbor v0.2.0

This release focuses on observability, alerting and cluster operations. Every important action on your node is now logged to a structured activity log, critical events trigger instant push notifications via Email or Webhook (Discord, Slack, custom), and the cluster now supports full container and VM replication between nodes.

---

### ✨ New Features

#### 🔔 Notification System
Never miss a critical event again. Upcode Harbor can now push notifications to your Email inbox or any Webhook endpoint the moment something happens on your node.

- **Email (SMTP)**: STARTTLS (port 587) or SSL (port 465), multiple recipients, configurable From address, test button
- **Webhook**: auto-detects the endpoint type:
  - **Discord** → rich Embed with title, colour coding (🟢 success / 🔴 failure) and description
  - **Slack** → native Incoming Webhook `{"text": "..."}` format
  - **Custom / generic** → `{"event": ..., "message": ..., "source": "upservx"}`
- **Node identification**: every notification includes `[Node: hostname]` in subject and body — useful in multi-node setups
- **Email subject format**: `[hostname] Upcode Harbor – Event Name`
- **12 per-event toggles** (all enabled by default):

| Category | Events |
|---|---|
| Container | Create, Start, Stop, Crash, Delete |
| VM | Create, Start, Stop, Delete |
| Backup | Success, Failure |
| System | Alert |

- **Rich context per event**:
  - Container create → image name, port mappings, volume mounts
  - Container start / stop / delete → runtime type (DOCKER / LXC / K8S)
  - VM create → CPU cores, memory MB, network bridge, disk count
  - Backup success → size in MB, backup path
  - Backup failure → full error message
- Configuration persisted to `/etc/upservx/notifications.json`
- All notification activity (send success, send error, dispatch) written to the activity log
- **Settings UI**: new *Notifications* tab (4th tab) with Email, Webhook and Events cards

#### 📋 Structured Activity Logging
All backend operations are now written to `/var/log/upservx/activity.log` in a consistent `YYYY-MM-DD HH:MM:SS [TAG] Message` format. The log level (INFO / ERROR) is set automatically.

| Module | Tag | Events logged |
|---|---|---|
| `containers.py`, `api/images.py` | `[CONTAINER]` | Create, volume/storage create/delete, image pull/delete |
| `vms.py` | `[VM]` | Create, start, stop, delete, clone, update, snapshot create/delete/restore |
| `storage.py` | `[STORAGE]` | Mount (incl. fstab), unmount, format, ZFS pool create |
| `network.py` | `[NETWORK]` | Interface configure, DNS save |
| `users.py` | `[USER]` | User/group create, update, delete |
| `services.py` | `[SERVICE]` | Start, stop, enable, disable |
| `firewall.py` | `[FIREWALL]` | Rule add/delete, chain flush/policy, port forward, masquerade, save/load |
| `reverse_proxy.py` | `[PROXY]` | Config create/delete, SSL obtain/renew/revoke |
| `app_store.py` | `[APPSTORE]` | App install, uninstall |
| `isos.py` | `[ISO]` | Download, upload, delete |
| `ssh_keys.py` | `[SSH]` | Key generate/store/delete, authorized_keys setup |
| `api/cluster.py` | `[SYSTEM]` | All 174 cluster print() calls now dual-write via `_clog()` |
| `settings.py` (VPN) | `[VPN]` | Tunnel start, stop |

#### 🔁 Cluster Replication System
Replicate containers and VMs between cluster nodes directly from the Cluster Management UI.

- New *Replication* table with columns: Origin Node, Destination Node, Name, Type, Sync Schedule
- Dynamic resource loading from the selected origin node (containers + VMs)
- Replication config persisted to `/etc/upservx/replications.json`
- Manual trigger via Play button per replication entry
- **Container replication**: full `docker save` export including volumes, port mappings, environment variables, restart policy and command; restored via `docker load`
- **VM replication**: `virsh dumpxml` export with all `.qcow2` disk images as tar.gz; restored via `virsh define` with automatic disk path patching and UUID regeneration

#### 🗄️ Persistent Storage Mounting
- Drives mounted via Storage Management UI are now automatically added to `/etc/fstab` using UUID-based identification
- Unmount removes the fstab entry automatically
- Intelligent default mount options per filesystem type (ext4, ntfs, vfat, exfat, xfs)
- fstab is backed up before every modification

### 🔒 Security Fixes

| Fix | Detail |
|---|---|
| WebSocket shell auth | `/system/shell` now authenticates via PAM before accepting — previously any unauthenticated client could open an interactive root shell |
| Debug endpoint removed | `/debug/echo` replaced with 404 |
| Path traversal (ISO) | `_safe_iso_path()` added; all ISO paths go through `os.path.realpath()` |
| SSRF (ISO download) | Non-http/https schemes and private/RFC-1918 ranges blocked |
| Path traversal (tarfile) | `_safe_tar_extractall()` prevents CVE-2007-4559-class extraction attacks |
| Exception detail leak | `/auth/login` returns generic "invalid credentials" on internal errors |
| Rate limiting | `/auth/login` limited to 10 attempts / IP / 60 s |
| Stale middleware bypass | `/metrics` exclusion removed (correct route `/cluster/node/metrics` is authenticated) |
| Input validation (users) | `_validate_name()` guards all user/group functions against shell metacharacter injection |
| Path traversal (SSH keys) | `_safe_key_path()` validates `key_name` with `^[a-zA-Z0-9_\-\.]{1,64}$` |
| Shell allowlist (users) | Shell path validated against `LOGIN_SHELLS` in create/update user |
| Logout response bug | `Response(content=dict(...))` → proper JSON string |

### ⚙️ API Changes

**New endpoints:**

| Method | Path | Description |
|---|---|---|
| `GET` | `/settings/notifications` | Get notification configuration |
| `POST` | `/settings/notifications` | Save notification configuration |
| `POST` | `/settings/notifications/test/email` | Send test email |
| `POST` | `/settings/notifications/test/webhook` | Send test webhook |
| `POST` | `/cluster/replications` | Create replication entry |
| `GET` | `/cluster/replications` | List replication entries |
| `DELETE` | `/cluster/replications/{id}` | Delete replication entry |
| `POST` | `/cluster/replications/{id}/trigger` | Trigger replication manually |
| `POST` | `/cluster/export/{type}/{name}` | Export container or VM |
| `GET` | `/cluster/download/{filename}` | Download exported archive |
| `POST` | `/cluster/upload` | Upload archive to node |
| `POST` | `/cluster/import/{type}` | Import container or VM |

**Changed:**
- Cluster metrics endpoint moved from `/metrics` to `/cluster/node/metrics`
- Auth middleware now also accepts master cluster key as Bearer token
- Replication endpoints bypass PAM middleware and handle auth internally

### 📦 Upgrade Notes

After updating, the service will automatically create `/var/log/upservx/` and `/etc/upservx/notifications.json` on first run. No manual migration required.

If you are running a multi-node cluster, ensure all nodes are updated to v0.2.0 before using the replication feature.
